# vibe-spec 스킬 사용설명서

> 요약: 개발을 모르는 사람이 AI로 무언가를 만들기 **전에**, 쉬운 질문으로 요구사항을 정리하고(1단계), 그걸 단계별 계획 지도 HTML과 단계 시작 파일로 그려 주며(2단계), 만드는 도중 바뀐 생각을 판(버전) 단위로 계획에 반영(3단계)하는 스킬입니다.

---

## 1. 한눈에 보기

| 항목 | 내용 |
|---|---|
| 스킬 이름 | `vibe-spec` |
| 대상 | 개발 경험이 없는 사람, 바이브 코딩 입문자 |
| 해결하는 문제 | 무엇을 만들지 정하지 않고 시작해서 방향이 계속 바뀌고, 끝났는지 스스로 판단하지 못하는 것 |
| 주요 결과물 | `requirements.md`, `plan.html`, `단계-시작-파일/01-….md` 등 |
| 필요 환경 | Python 3 (표준 라이브러리만 사용, 추가 설치 없음) |
| 쓰지 않는 경우 | 요구사항이 이미 확정되어 코드를 짜는 중일 때, 이미 만든 것을 기록으로 남길 때(이 경우 `dev-replay` 스킬) |

## 2. 이럴 때 불러내세요

아래와 비슷한 말을 하면 스킬이 동작합니다.

- "뭘 만들지부터 같이 정해줘"
- "요구사항 정리해줘" / "기획서 써줘"
- "바이브 코딩 시작하려는데 뭐부터 해야 해?"
- "개발 계획 세워줘" / "계획을 그림으로 보여줘"
- "이 md 빈칸 채워줘" (빈칸 템플릿을 첨부한 경우)
- 아이디어만 던지며 "이거 만들 수 있어?"라고 물을 때도 코딩 전에 이 스킬을 먼저 제안합니다

## 3. 전체 흐름

```
[1단계] 요구사항 채우기  →  requirements.md
          (spec_check.py 로 빈칸 0개 될 때까지)
               ↓
[2단계] 계획 그리기      →  plan.html + 단계-시작-파일/*.md
          (build_plan.py)
               ↓
   단계별로 시작 파일을 새 대화에 올려 개발 진행
               ↓
[3단계] 계획 고치기      →  plan.json 판 2, 3 ... + 새 plan.html
          (revise_plan.py → build_plan.py)
```

## 4. 1단계 — 요구사항 채우기

### 진행 방식

- 빈칸 있는 MD를 가져오면 그 파일을, 없으면 `assets/requirements-template.md`를 씁니다
- `spec_check.py`가 빈칸을 줄 번호와 함께 찾아내고, **비어 있는 칸만** 질문합니다
- 질문은 한 번에 최대 3개, 가능하면 선택지 형태로 합니다
- 데이터베이스·배포·API·인증 같은 전문용어는 질문에 쓰지 않습니다
- 모른다고 답하면 흔한 기본값으로 대신 채우고 "나중에 바꿔도 된다"고 알려 줍니다
- 답을 받으면 "그러니까 ○○이 ○○할 때 ○○하려는 거군요"처럼 되돌려 확인합니다

### 대신 정해 주지 않는 칸 3개

| 칸 | 기준 |
|---|---|
| 쓸 사람 | "모두"는 안 됨. 한 사람을 구체적으로 |
| 이게 되면 끝(완료 기준) | 눈으로 확인 가능해야 함. 예: "사진을 올리면 10초 안에 목록이 뜬다" |
| 안 만들 것 | 최소 2개. 비우면 범위가 끝없이 늘어남 |

### 요구사항 템플릿의 12개 절

1. 한 줄로 말하면
2. 왜 만드나요 (지금 방식 / 불편한 점 / 바뀌는 점)
3. 누가 쓰나요 (사람 / 익숙한 정도 / 기기)
4. 쓰는 순서
5. 꼭 있어야 하는 것 (요구사항별: 무엇을 / 이게 되면 끝 / 없으면)
6. 있으면 좋은 것
7. 안 만들 것
8. 정보 (저장할 것 / 민감 정보 / 기존 자료)
9. 겉모습 (참고 서비스 / 분위기)
10. 사정 (기한 / 만드는 사람 / 올릴 곳 / 비용)
11. 이게 되면 끝 (한 문장)
12. 아직 모르는 것

### 개수 규칙

- 필수 요구사항은 **3~5개**
- 8개처럼 많으면 "이 중 하나만 되고 나머지가 다 안 되면 그래도 쓰시겠어요?"로 순위를 매겨 나머지는 "있으면 좋은 것"으로 내립니다

## 5. 2단계 — 계획 그리기

### 단계를 나누는 기준

- 단계는 **4~7개**, 한 단계는 대화 2~6번 분량
- 한 단계는 **사용자가 혼자 끝났는지 확인할 수 있는 덩어리**
- 눈에 보이는 화면부터 → 저장 → 관리 → 실제 사용 순
- 첫 단계는 작게, 마지막 필수 단계는 "실제로 한 번 써 보기"
- 나중에 할 단계는 지우지 않고 `phase: "later"`로 두면 페이지에 "여기까지가 1차 출시" 선이 그어집니다

| 이렇게 쓰지 않음 | 이렇게 씀 |
|---|---|
| 백엔드 구축 | 주문을 넣고 브라우저를 껐다 켜도 남아 있게 하기 |
| 인증 구현 | 링크를 아는 사람만 들어오게 막기 |
| 테스트 | 실제 손님 세 분께 링크를 보내 주문받아 보기 |

### plan.json 주요 필드

| 위치 | 필드 | 설명 |
|---|---|---|
| project | `title`, `slug`, `oneLiner`, `who`, `deadline`, `where`, `aboutMe` | 프로젝트 기본 정보. `aboutMe`는 모든 시작 파일의 "저에 대해"에 들어감 |
| 최상위 | `requirements` | `{id, title, done, must}` 배열 |
| 최상위 | `notMaking`, `openQuestions`, `risks` | 안 만들 것, 미정 사항, 위험 |
| 최상위 | `version`, `revisions` | 판 번호와 변경 내역. `revise_plan.py`가 채움(직접 쓰지 않음) |
| stages[] | `title`, `goal`, `phase`, `effort`, `tasks`, `outputs`, `reqs`, `risk` | 단계 정보 |
| stages[] | **`check`** | 내가 직접 확인할 것. 페이지의 체크박스와 진행률이 됨 (필수) |
| stages[] | **`ask`** | 그 단계에서 AI에게 부탁하는 말 한 문단. 사용자 말투로 (필수) |

전체 예시는 `assets/example-plan.json`(동네 반찬가게 주문받기, 5단계)에 있습니다.

### 빌드 결과물

- `plan.html` — 브라우저로 여는 계획 지도. 단계별 체크박스, 진행률, 요구사항 내려받기 버튼, 단계 시작 파일 내려받기 버튼, "바꾸고 싶은 것" 입력 칸
- `단계-시작-파일/01-….md` … — 단계 수만큼 생성. 새 대화에 올리고 "이 파일대로 시작해 줘"라고만 하면 됨

### 단계 시작 파일의 고정 구성

모든 단계가 같은 순서라 두 번째 파일부터는 읽지 않고 올려도 됩니다.

1. 무엇을 만드는 중인가
2. 지금까지 된 것 (앞 단계 요약, 처음부터 다시 만들지 말라는 문장)
3. 이번 단계에서 할 일
4. 부탁하는 것 (`ask`)
5. 끝나면 이런 것이 있어야 합니다
6. 제가 직접 확인할 것 (체크 상자)
7. 지키기로 한 것 (`notMaking` + 단계 `risk`)
8. 저에 대해 (`aboutMe`)
9. 이번 단계의 범위 (다음 단계 이름, 벗어나지 말 것)

### 빌드 후 경고("살펴볼 것")가 뜨는 경우

- 단계가 8개 이상
- `check`나 `ask`가 없는 단계
- 만드는 단계가 없는 요구사항
- 비어 있는 "이번에는 만들지 않는 것"

## 6. 3단계 — 개발 중에 계획 고치기

### 변경 요청 가져오는 법

- `plan.html`의 각 단계에 있는 "이 단계에서 바꾸고 싶은 것" 칸에 적어 둡니다 (브라우저에 저장되어 다시 열어도 남음)
- 위쪽 **바꾸고 싶은 것 모으기** 버튼으로 수정 요청서 한 장을 만들어 복사하거나 `.md`로 내려받아 대화에 가져옵니다
- 그냥 말로 "이거 바꾸고 싶어"라고 해도 됩니다

### 변경을 네 갈래로 나눔

| 갈래 | 신호 | 처리 |
|---|---|---|
| 못 알아들은 것 | "이게 아니라…" | 단계 유지, `check`를 더 구체적으로 |
| 빠뜨린 것 | "당연히 되는 줄 알았어요" | 요구사항에 추가, 만들 단계 지정 |
| 새로 생긴 욕심 | "기왕 하는 김에…" | **기본은 뒤로** (`later` 또는 "있으면 좋은 것") |
| 틀린 판단 | 그 방향이 안 통함 | 단계 변경·삭제, 요구사항까지 거슬러 다시 질문 |

"지금 넣으면 1차 출시가 그만큼 밀립니다. 그래도 지금 하시겠어요?"라고 한 번 묻는 것이 핵심입니다.

### 판 기록

- `revise_plan.py`는 계획을 대신 고치지 않고, 두 판을 비교해 **무엇이 바뀌었는지만** 판 번호와 함께 기록합니다
- 새 페이지 제목 옆에 "판 2"가 붙고 아래에 변경 내역이 쌓입니다
- 1차 단계 증가, 필수 요구사항 증가, "만들지 않을 것" 감소 시 범위 증가 경고가 뜹니다 → 늘어난 만큼 무엇을 미룰지 정해야 합니다
- 요구사항이 바뀌었으면 `requirements.md`도 같이 고칩니다

## 7. 스크립트 사용법

| 스크립트 | 명령 | 역할 |
|---|---|---|
| `spec_check.py` | `python3 scripts/spec_check.py 요구사항.md [--json]` | 빈칸 목록과 채운 비율 출력. 다 채워지면 종료 코드 0, 아니면 1 |
| `build_plan.py` | `python3 scripts/build_plan.py plan.json --out 출력폴더 [--spec 요구사항.md] [--no-scrub]` | `plan.html`과 단계 시작 파일 생성 |
| `revise_plan.py` | `python3 scripts/revise_plan.py 지난.json 고친.json --why "이유 한 줄" [--out 경로] [--date YYYY-MM-DD]` | 판 번호와 변경 내역 기록. `--out` 없으면 고친 파일에 덮어씀 |

참고 사항:

- `build_plan.py`는 기본적으로 API 키처럼 보이는 문자열(`sk-ant-…`, `ghp_…`, `AKIA…`, `AIza…` 등)을 `***`로 가립니다. 끄려면 `--no-scrub`
- `stages`가 비어 있으면 빌드가 중단됩니다
- `revise_plan.py`는 두 파일에 차이가 없으면 중단됩니다

## 8. 빠른 사용 예시

```bash
# 1) 빈칸 확인
python3 scripts/spec_check.py requirements.md

# 2) 계획 빌드
python3 scripts/build_plan.py plan.json --out ./out --spec requirements.md

# 3) 개발 중 수정 후 재빌드
cp plan.json plan-v2.json   # 사본에서 고친 뒤
python3 scripts/revise_plan.py plan.json plan-v2.json --why "사진 기능은 2차로 미룸"
python3 scripts/build_plan.py plan-v2.json --out ./out --spec requirements.md
```

실제 대화에서는 스크립트를 직접 돌릴 필요 없이 Claude에게 "요구사항 정리해줘"처럼 말하면 Claude가 위 과정을 대신 수행합니다.

## 9. 폴더 구조

```
vibe-spec/
├── SKILL.md                         스킬 본문(동작 규칙)
├── references/
│   ├── interview.md                 절별 질문 문장, 전문용어 바꿔 말하기, 기본값
│   ├── plan-rules.md                단계 쪼개기 규칙, plan.json 전체 필드
│   └── revising.md                  변경 네 갈래 분류 기준과 되묻는 문장
├── assets/
│   ├── requirements-template.md     빈칸 요구사항 템플릿(사용자에게 그대로 줘도 됨)
│   ├── stage-brief-template.md      단계 시작 파일 고정 틀
│   ├── example-plan.json            채워진 계획 예시
│   └── plan-template.html           계획 페이지 원본
└── scripts/
    ├── spec_check.py                빈칸 검사
    ├── build_plan.py                계획 페이지·시작 파일 생성
    └── revise_plan.py               판 비교·기록
```

## 10. 자주 어긋나는 것

- 인터뷰 없이 Claude가 요구사항을 지어냄 → 사용자 것이 아니라 나중에 "이게 아닌데"가 나옴
- 질문을 한꺼번에 쏟음 → 3개씩 끊기
- "안 만들 것"을 비워 둠
- 완료 기준이 추상적임 ("잘 된다", "편해진다")
- 단계 이름에 개발 용어 사용
- `ask`를 빈칸으로 둠 → 시작 방법이 없어 첫 줄에서 멈춤
- 변경 요청을 받는 족족 1차에 넣음
- 계획만 고치고 요구사항은 안 고침 → 두 문서가 어긋남

## 11. 설치

- 완료 후에는 기록용으로 `dev-replay` 스킬과 이어 쓰도록 설계되어 있습니다
