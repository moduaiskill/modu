# 계획 쪼개기와 plan.json

## 단계를 나누는 기준

한 단계는 **끝났는지 사용자가 혼자 확인할 수 있는 덩어리**다. 이 기준 하나만 지켜도 계획이 쓸모 있어진다.

- 단계는 4~7개. 그 이상이면 비전공자가 따라가지 못한다.
- 각 단계는 대화 2~6번 안에 끝나는 크기로 잡는다. 그보다 크면 쪼갠다.
- 눈에 보이는 것부터. 화면 → 저장 → 관리 → 실제 사용 순서가 대개 잘 맞는다.
- 첫 단계는 반드시 작게 잡는다. 첫 성공이 빠를수록 끝까지 간다.
- 마지막 필수 단계는 "실제로 한 번 써 보기"로 둔다. 만들기만 하고 안 써 보면 무엇이 틀렸는지 영원히 모른다.

나쁜 단계와 좋은 단계:

| 이렇게 쓰지 않는다 | 이렇게 쓴다 |
|---|---|
| 백엔드 구축 | 주문을 넣고 브라우저를 껐다 켜도 남아 있게 하기 |
| UI 개선 | 60대 사장님이 혼자 주문 목록을 찾을 수 있게 화면 줄이기 |
| 인증 구현 | 링크를 아는 사람만 들어오게 막기 |
| 테스트 | 실제 손님 세 분께 링크를 보내 주문받아 보기 |

## 1차 출시 경계

`phase`를 `later`로 둔 단계 앞에 "여기까지가 1차 출시" 선이 그어진다. 나중에 할 것을 아예 지우지 말고 `later`로 남겨 두는 편이 낫다. 지우면 사용자가 잊힐까 봐 불안해하고, 남겨 두면 지금 안 해도 되는 이유가 생긴다.

## plan.json 필드

### project

| 필드 | 설명 |
|---|---|
| `title` | 만들 것의 이름 |
| `slug` | 파일 이름과 진행 저장에 쓰인다. 없으면 title에서 자동 생성 |
| `oneLiner` | 요구사항 1번 칸 그대로 |
| `who` | 쓸 사람. 구체적일수록 좋다 |
| `deadline` | "3주 안" 같은 자유 문자열 |
| `where` | 어디에 올릴지 |

### 최상위

| 필드 | 설명 |
|---|---|
| `requirements` | `{id, title, done, must}` 배열. 단계의 `reqs`가 `id`를 가리킨다 |
| `stages` | 단계 배열. 순서가 곧 진행 순서다 |
| `notMaking` | 이번에 만들지 않는 것. 문자열 배열 |
| `openQuestions` | 아직 정하지 못한 것 |
| `risks` | 문자열 배열 또는 `{what, plan}` 배열 |
| `version` | 판 번호. `revise_plan.py`가 채운다. 손으로 적지 않는다 |
| `revisions` | 바뀐 내역. 역시 `revise_plan.py`가 채운다 |

### stages[]

| 필드 | 설명 |
|---|---|
| `title` | 단계 이름. 개발 용어 없이 |
| `goal` | 이 단계가 끝나면 무엇이 달라지는지 한 줄 |
| `phase` | `later`면 1차 출시 이후로 밀린다. 비워 두면 1차에 포함 |
| `effort` | "대화 3~5번" 처럼 사용자가 가늠할 수 있는 단위. 시간 단위는 잘 맞지 않는다 |
| `tasks` | 여기서 하는 일 |
| `outputs` | 끝나면 생기는 것 |
| `check` | **내가 직접 확인할 것.** 체크박스가 되고 진행률이 된다. 클릭해서 눈으로 볼 수 있는 행동으로 |
| `ask` | **그 단계에서 부탁하는 말 한 문단.** 시작 파일의 "부탁하는 것" 절이 된다 |
| `reqs` | 이 단계가 만드는 요구사항 id |
| `risk` | 이 단계에서 어긋나기 쉬운 것 한 줄 |

## 단계 시작 파일

단계마다 같은 틀의 `.md` 파일 하나가 만들어진다. 사용자는 그 단계를 시작할 때 **파일을 대화에 올리고 "이 파일대로 시작해 줘"라고만 말하면 된다.** 긴 글을 복사해 붙여 넣을 일이 없다.

파일은 `build_plan.py`가 계획에서 뽑아 만든다. 손으로 쓰지 않는다. 틀은 `assets/stage-brief-template.md`에 있고 모든 단계가 같은 순서를 따른다.

| 절 | 어디서 오나 |
|---|---|
| 무엇을 만드는 중인가 | `project.oneLiner`, `who`, `where` |
| 지금까지 된 것 | 앞선 단계들의 제목과 목표. 첫 단계면 "빈 상태에서 시작" |
| 이번 단계에서 할 일 | `goal`, `tasks` |
| 부탁하는 것 | `ask` |
| 끝나면 이런 것이 있어야 합니다 | `outputs` |
| 제가 직접 확인할 것 | `check` (체크 상자로) |
| 지키기로 한 것 | `notMaking` 전체와 그 단계의 `risk` |
| 저에 대해 | `project.aboutMe`. 없으면 기본 문구 |
| 이번 단계의 범위 | 다음 단계 이름. 벗어나지 말라는 문장 |

이 구조 덕분에 대화를 새로 시작해도 AI가 맥락을 잃지 않는다. 비전공자가 긴 대화에서 겪는 가장 큰 문제가 이것이다.

### ask 칸 쓰는 법

시작 파일의 "부탁하는 것" 절에 그대로 들어간다. 세 가지를 지킨다.

- **사용자의 말투로 쓴다.** "구현해 주세요"가 아니라 "만들어 줘".
- **한 단계에서 할 일만 담는다.** 전체 프로젝트를 설명하지 않는다. 앞 단계에서 이어진다는 전제로 쓴다.
- **다른 절과 겹치지 않게 쓴다.** 확인 기준이나 만들지 않을 것은 이미 다른 절에 들어간다. 여기서 반복하지 않는다.

빈칸을 남겨야 할 때는 괄호로 표시한다. 예: "어제 써 보니 이런 점이 불편했어: (여기에 적기)".

### project.aboutMe

사용자가 자기 상황을 적는 칸이다. 시작 파일마다 들어가서, 매번 "저는 개발을 몰라요"라고 설명하지 않아도 되게 만든다. 비우면 기본 문구가 들어간다.

## 빌드

```bash
python3 scripts/build_plan.py plan.json --out ./out --spec requirements.md
```

`plan.html` 과 함께 `단계-시작-파일/` 폴더에 `01-….md`, `02-….md` 가 단계 수만큼 만들어진다. 페이지 안에도 같은 내용이 담겨 있어서, 사용자는 페이지에서 바로 내려받아도 되고 폴더에서 꺼내 써도 된다.

끝나면 살펴볼 것이 함께 출력된다. 아래 경우에 나온다.

- 단계가 8개 이상
- 확인 항목이나 `ask`가 없는 단계
- 만드는 단계가 없는 요구사항
- 비어 있는 "이번에는 만들지 않는 것"

전부 계획이 실제로 굴러가지 않게 되는 지점들이다. 채워서 다시 만든다.
